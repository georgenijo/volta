## Meter outage and recovery

Commander retains an already managed config during a short consumer/receiver
restart or reboot ordering delay only if durable last-complete accounting plus
1,000 signals/second per configured VIN, elapsed since accounting and a 30-second
margin stays strictly below `$23` and the `$28` shared operating line. Grace is
at most five minutes, durably tracked across restarts. A missing baseline or
unsafe projection deletes immediately. At UTC rollover, previous-month accounting
permits grace only for the first five minutes; current-month burn starts at 00:00Z.
The meter reports current-month `starting` until the new total is refreshed.

Inspect private `/v1/telemetry/status` for `unknownSince`, `lastKnownThrough`,
`stopReason` and pending DELETE/retry. Do not issue an operator POST merely to
clear a transient meter error. A prolonged outage deletes and latches `meter_*`;
after DELETE succeeds, **ten continuous minutes** of fresh complete accounting
below `$20` and the shared line, then successful paired-key/client preflight,
permit automatic recreation. Missing/incomplete accounting or a check gap longer
than the freshness window restarts those ten minutes. Each vehicle has at most
**three automatic resume attempts per UTC month**; attempts and the 10/20/40-minute
exponential cooldown are saved before paid preflight and survive successful
creates/deletes and process restarts. After the cap, `auto_resume_limit` requires
operator action, including across rollover. 429/5xx/CA/OAuth failures cannot poll
every reconciliation tick. An unpaired key
or old client records `resume_*` and requires operator action; exhausted normal
call allowance records `budget_stop`. Budget, operator DELETE and uncertain create/update latches
never auto-resume. Every create, resume, economy update and renewal requires
remaining reserve for **two fresh DELETE attempts for the target configuration**
plus every other possibly-live config's unused two-attempt claim;
refusal returns `telemetry_delete_reserve_insufficient` (HTTP 429), with
`delete_reserve_stop` for an automatic recovery/update. DELETE reservations persist per-config attempts and preserve each other
possibly-live config's unused two-attempt claim, including repeated operator
DELETEs. Every vehicle can spend both its own attempts without stranding the
last call. This is headroom for a
successful delete and one retry, not a guarantee against unlimited network/OAuth
failures. A refused first create incurs no config DELETE; pending/unknown POST
outcomes remain owned until a successful DELETE. Operator DELETE returns
HTTP 409 `telemetry_config_not_owned` if local state proves no created/confirmed
config; it does not claim rollback succeeded. A successful remote DELETE saves
`deleteConfirmed:true`; repeated operator DELETE then returns 200
`alreadyDeleted:true` without meter/OAuth or another paid DELETE. A new config
POST or confirmed external config clears that proof. For a target never
configured by commander, 409 is expected: verify independently that no external
config exists before disabling services; `synced:false` alone may be adoption
pending and is not proof of absence. A successful remote status read
with `synced:true` establishes conservative ownership of an external config,
so a subsequent operator DELETE contacts Tesla and remains pending on failure. Inspect `configMayExist`,
`autoResumeMonth`, `autoResumeAttempts`, `nextResume`, `healthySince` and
`lastHealthyCheck` in status. A budget stop observed while meter-latched makes that latch
permanent until an operator create. Ordinary paid-call allowance still applies
to resume; OAuth/network failure can delay either DELETE or re-create.

## Stop and rollback

Delete **before** disabling guard, OAuth or meter:

```sh
fleet exec --timeout 60 ubuntu -- 'sudo curl --fail --silent --config /etc/volta/commander-operator.curl -X DELETE http://127.0.0.1:8090/v1/vehicles/1/telemetry/config'
fleet exec --timeout 30 ubuntu -- 'sudo curl --fail --silent --config /etc/volta/commander-operator.curl http://127.0.0.1:8090/v1/telemetry/status'
# Only after DELETE returned 2xx AND profile=stopped AND no pendingAction; retain history/secrets:
fleet exec --timeout 60 ubuntu -- 'sudo /opt/volta/deploy/telemetry/funnel/rollback-funnel.sh --apply; sudo docker compose --env-file /opt/volta-telemetry/telemetry.env -f /opt/volta/deploy/telemetry/compose.yaml stop receiver consumer redpanda; sudo systemctl disable --now volta-telemetry-cert.timer'
```

Pending DELETE requires the guard/meter/OAuth to stay available. Remove API opt-in
and restore the previous reviewed API revision separately. Preserve encrypted
commander state and receipts through restart/rebuild. Ordinary rollback never
deletes schemas/history, uses down --volumes, resets Funnel, rotates keys/tokens,
or touches unrelated workloads. Tesla/network failure can prevent timely DELETE;
the portal billing limit is the final external safety boundary.

Known gap: the $23 stop only deletes configs commander believes it owns. If
commander state is lost, wiped or restored from an older backup while a config
is live, the meter can report `stop` with signals still arriving and no DELETE
is sent. Treat that as an incident: run the operator status read (a `synced:true`
result adopts the config) and then the operator DELETE above; until then only
the portal billing limit and the config's 30-day expiry bound spend.
